## SSE server contract (`toolkit/live_server.py`, `scripts/serve_workspace.py`)

- Stdlib only: `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`.
  Binds `127.0.0.1` by default. No third-party code, no WebSocket.
- Routes:
  - `GET /` — the workspace UI page: the exact output of
    `toolkit/workspace_ui.render_events_html` for the current contents
    of the events file (reference time: the latest event ts, the
    renderer's default). Byte-identical to what
    `scripts/render_workspace.py` would write for the same file.
  - `GET /events` — the SSE stream: `Content-Type: text/event-stream`,
    `Cache-Control: no-cache`, one `data: <event JSON>\n\n` frame per
    event, in file order, each frame the event's canonical JSON
    (sorted keys, compact separators — the same bytes as the log
    line). After the last event the server sends one terminal frame,
    `event: end` with `data: {"run_id": "<run id or null>",
    "events": <number of events streamed>, "status": "done"}`, and
    then closes the stream.
  - Any other path: `404` with a short plain-text body. No other
    route exists.
- Modes (CLI `--mode`, server argument `mode`):
  - `recorded` — reads the whole events file once and streams it in
    order, then the `end` frame. This is the mode that streams a
    recorded `events.jsonl` live, one event per line.
  - `tail` (default) — streams the events already in the file, then
    polls the file every 0.2 s for appended lines and streams each new
    line as it appears, until a `run_finished` event has been
    streamed, then the `end` frame. This is the mode that follows a
    live run as it appends to its `events.jsonl`.
- Missing or empty events file: NEVER a crash. `recorded` mode on a
  missing/empty file streams zero `data:` frames and then the `end`
  frame (`"events": 0`, `"run_id": null`); `tail` mode on a missing
  file waits for it to appear (same poll); `GET /` on a missing/empty
  file renders the renderer's empty-log page ("No events recorded
  yet"). A malformed JSON line raises the same error
  `toolkit.events.load_events` raises — a broken log is reported,
  never silently skipped.
- Client disconnect: the handler stops writing and the thread ends;
  a disconnect is not an error and is not logged as one.
- CLI: `python3 scripts/serve_workspace.py [--events PATH]
  [--host 127.0.0.1] [--port 8000] [--mode tail|recorded]`.
  Defaults: `--events examples/agent-run-events.jsonl`, `--port 8000`,
  `--mode tail`. `--port 0` selects an ephemeral port (used by the
  tests). The server prints one line on start (`Serving <mode> <events
  path> on http://<host>:<port>`) and serves until interrupted
  (Ctrl-C / SIGINT exits 0). Exit 1 only on a bad `--mode` or an
  unbindable port.

## Recorded-run replay page contract (`toolkit/live_replay.py`, `scripts/render_replay.py`)

- A static page generated from the U.1 fixture by REUSING
  `toolkit/workspace_ui.render_events_html` — the replay page is the
  U.2 render plus three additions, never a second renderer. It works
  as a static file with no server: no JavaScript, no fetch, no
  external reference (same rule as the U.2 render).
- Home: `docs/workspace-replay.html` (the GitHub Pages location; the
  repo has no Pages config file, so `docs/` is the conventional
  Pages source and the page is placed there rather than in
  `examples/`, where the U.2 render example lives).
- The page MUST carry, prominently, directly under `<body>`, a banner
  (`<div id="recorded-demo-banner" role="note">`) whose text contains
  the exact lowercase phrase `recorded demo`, the run date, and the
  provider used. Exact wording, fixed here:
  - Heading: `Recorded demo`.
  - Body: `This is a recorded demo of run u1-fixture-run — a replay
    of a past run, not a live run. Run date: 2026-11-14. Provider:
    FAKE (fake provider — synthetic demo data, no live data, no
    real cost).`
  - The run date is DERIVED from the `run_started` event's `ts`
    (date part), never typed. The provider is a caller-supplied
    parameter (`provider="FAKE"` by default in the CLI); the fixture
    provider IS the fake provider, and it is labelled honestly as
    such — never as a real provider, never as live data.
- The replay page also contains the cost/latency meter card and the
  run-diff section (below), inserted directly after `</header>` in
  that order: meter first, diff second.
- CLI: `python3 scripts/render_replay.py [--events PATH]
  [--diff-events PATH] [--output PATH] [--reference-time ISO]
  [--provider FAKE]`. Defaults: `--events
  examples/agent-run-events.jsonl`, `--diff-events
  examples/agent-run-events-2.jsonl`, `--output
  docs/workspace-replay.html`, `--reference-time 2026-11-14T12:00:12Z`
  (the U.2 protocol's fixed reference time, so the fixture stamps
  read `12s ago`), `--provider FAKE`. Exit 0 on success, printing
  the output path and the event count; exit 1 when either input file
  is missing or a log fails U.1 validation.
- The committed replay page is byte-identical on re-render with the
  same arguments (same determinism rule as the U.2 render).

## Run diff view definition (`toolkit/live_replay.py`)

- `diff_runs(events_a, events_b)` is a pure function of two event
  lists (file order, each validated with
  `toolkit.events.validate_event`). It returns a dict with the run
  ids, the counts, and three lists: `added`, `removed`, `changed`,
  plus `step_status_changes`.
- Identity: two events are the SAME slot when their identity key
  matches. The key is `(type, step, tool, symbol, source, gate,
  section, speaker)` — only the fields present on the event are part
  of the key. `schema_version`, `run_id`, `seq`, `ts` and `prev_hash`
  are NEVER part of the key: they differ between any two runs by
  construction and must not manufacture differences.
- Matching: within one key, events are paired in file order (first
  unpaired event in A with that key pairs with the first unpaired
  event in B with that key). An event in B with no pair in A is
  `added`; an event in A with no pair in B is `removed`. A pair whose
  remaining content fields differ is `changed`: the compared content
  fields are `status`, `verdict`, `text`, `reason`, `n_points`,
  `detail`, `last_date`, `stance`, `steps`, `team`, `exchange`,
  `market`, `symbols`. A `changed` entry carries the old and the new
  content dicts.
- Per-step status changes: for every step that appears in either run,
  derive its status with the SAME rule as the U.2 renderer
  (`done` when a `tool_result` for the step has status `"ok"`,
  `failed` when one has status `"failed"`, `in progress` when a
  `step_started` exists but no result yet, `not started` otherwise;
  a step with both an ok and a failed result counts as `failed`).
  A step whose derived status differs between the runs is a
  `step_status_changes` entry (`step`, `before`, `after`).
- Rendering: `render_diff_html(diff)` renders one
  `<section id="run-diff">` with a summary line
  (`"<n> added, <n> removed, <n> changed; <n> per-step status
  changes"`) and one line per added/removed/changed entry (event
  type plus its key fields, escaped) and per step-status change.
  Deterministic: same two logs render byte-identical HTML (file
  order everywhere, no set iteration).
- Pre-registered expected diff, fixture 1 vs fixture 2 (pinned here,
  asserted in tests): **4 added, 1 removed, 0 changed, 0 per-step
  status changes**. Added: `evidence_ref` source `Paper C`;
  `debate_turn` speaker `bull_agent` (stance `bull`); `gate_result`
  gate `risk_limits` (verdict `PASS`); `memo_section` section
  `verdict`. Removed: `evidence_ref` source `Paper B`. Changed:
  none. Per-step status changes: none — all six steps are `done` in
  both runs.

## Cost/latency meter definition (`toolkit/live_replay.py`)

- `compute_cost_latency(events, rate_per_token_usd=0.0, tokens=None)`
  is a pure function of an event list (validated). It returns a dict:
  `n_calls`, `n_results`, `n_unmatched_calls`, `total_latency_s`,
  `mean_latency_s`, `slowest` (`{"tool", "step", "latency_s"}` or
  `None` when there is no matched pair), `per_tool` (latencies per
  tool, in file order), `cost_usd`, `cost_basis`.
- Latency: each `tool_call` is paired with its matching `tool_result`
  by the SAME pairing rule as the U.2 renderer (same `tool`, same
  `step`, the next `tool_result` after the call). Latency is
  `result_ts - call_ts` in seconds (float, from the ISO 8601
  timestamps). A call with no later matching result is unmatched and
  contributes no latency. Totals are exact sums of the pair
  latencies; the mean is the total divided by the number of matched
  pairs (0.0 when there are none). The slowest call is the matched
  pair with the largest latency; ties break by file order (first
  wins), so the result is deterministic.
- Cost: `cost_usd = (tokens or 0) * rate_per_token_usd`. BOTH inputs
  are caller-supplied; the U.1 schema records NO token counts, so a
  run's token count is never inferred from its events. The default
  rate is `0` and the default token count is `None` (treated as 0),
  so the default cost is `$0.00`. A real cost is shown ONLY when the
  caller supplies both a token count and a non-zero rate, and the
  rendered card then states the rate and the token count it was
  computed from. For the fake provider the cost is `$0.00` — a real
  cost is NEVER invented, and no per-token rate is ever assumed.
- Rendering: `render_meter_html(meter)` renders one
  `<section id="cost-latency-meter">` with the call/result/unmatched
  counts, total/mean/slowest latency, per-tool latencies, and the
  cost with its basis string. Deterministic, same input renders
  byte-identical HTML.
- Pre-registered expected values, computed by hand from the fixture
  timestamps and pinned in tests:
  - Fixture 1 (all 23 events at `2026-11-14T12:00:00Z`): 6 calls,
    6 results, 0 unmatched; every pair latency `0.0` s; total
    `0.0` s; mean `0.0` s; slowest `technical_read` (step
    `technical`), `0.0` s; cost `$0.00`.
  - Fixture 2 (advancing clock, +2 s per event from
    `2026-11-15T12:00:00Z`): 6 calls, 6 results, 0 unmatched;
    every pair latency `2.0` s; total `12.0` s; mean `2.0` s;
    slowest `technical_read` (step `technical`), `2.0` s
    (tie broken by file order); cost `$0.00`.

## Zero-decorative-animation rule

- NO CSS `animation`, `transition` or `@keyframes` anywhere in the
  rendered workspace/replay HTML, and no JavaScript-driven motion.
  The U.2 stylesheet already contains none; the banner, meter card
  and diff section added by this PR add plain static HTML and no
  stylesheet rules that move anything. The only motion the workspace
  may ever show is a state change that reflects a real event (for
  example a status chip changing when a new event arrives in live
  mode) — and this PR adds no such motion either: the live server
  streams events, it does not animate the page.
- Audit, stated here so it is checkable: grep the rendered HTML of
  both the workspace example and the replay page for `animation`,
  `transition` and `@keyframes` (case-insensitive) — zero matches
  expected. The same grep runs in `tests/test_live_replay.py`
  against the replay page output and the live server's `/` response.
  The `prefers-reduced-motion` position from the U.2 protocol stands:
  there is nothing to disable, because there is no animation at all.
